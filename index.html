What is a database? DD 1-2

  • A database is a centralized and structured set of data stored on a computer system.
  • It lets you retrieve, add, modify and delete data when required.
  • It also transforms retrieved data into useful information.
  • It is usually managed by a Database Administrator (DBA).
TermDefinition
DBMSSoftware for storing and retrieving users' data with security measures. Accepts requests for data from an application and instructs the OS to provide that data.
SQLStructured Query Language. The ANSI standard language for relational DBMSs. Used to update or retrieve data. Used by Oracle, Sybase, SQL Server, Access, Ingres…

Why Oracle Academy? Industry-relevant curriculum, free resources and a structured learning path. Oracle's main product is the Oracle Database, one of the most widely used relational DBMSs, especially in large enterprises.

Modern databases store many kinds of data: operational, media-rich, external, decision support and documents. Inside the database, data is stored raw. When it's queried, it is turned into useful information.

Data vs. Information DD 1-2

Data

Raw or unprocessed material.

e.g. one student's test score

Information

Knowledge or intelligence; data with a special meaning or function. Usually the result of combining, comparing, analyzing or calculating on data.

e.g. the class average or school average

Data in…Information out…
Yearly spending: 1997 $1,000,000, 1998 $2,000,000Next year's budget
Each student's test scoreClass average or school average
312 graduatesWhere are they going?
98% of students pass the Math examBy how much did results change?
💡 How to spot it

If it has been processed (averaged, totalled, compared), it is information. If it's a single recorded fact, it is data.

Conceptual, Logical & Physical models DD 2-1

1 · Conceptual: the blueprint

  • High-level business requirements, no technical detail. Builds common understanding between stakeholders and data architects.
  • Has: entities and relationships. Lacks: attributes, UIDs, technology.
  • Based on current needs but may reflect future needs. Covers what is conceptually ideal, not what is physically possible.

Why build a conceptual model? It describes exactly the information needs of the business, facilitates discussion, prevents mistakes and misunderstandings, forms "ideal system" documentation, forms a sound basis for physical design, documents the business rules, and takes regulations and laws into account.

2 · Logical: the detailed plan

  • Adds attributes and UIDs. Platform-independent. Called an entity relationship model (ERM), drawn as an ERD.
  • Sets attribute optionality and relationship optionality & cardinality.

3 · Physical: the implementation

  • Technology-specific. Adds data types (INTEGER, VARCHAR), table and column names, primary & foreign keys, views, indexes, and features for a specific DBMS (Oracle, MySQL, SQL Server).

Data modeling is capturing the important concepts and rules of a business and showing them visually on a diagram, which becomes the blueprint for the physical thing.

Entities, Instances, Attributes, UIDs DD 2-2

Entity

  • "Something" of significance to the business about which data must be known. Usually a noun: objects, events, people.
  • Can be tangible (PERSON, PRODUCT), intangible (SKILL LEVEL) or an event (CONCERT).
  • An instance is a single occurrence of an entity. Dalmatian, Siamese cat → instances of ANIMAL.
⚠️ Entity or instance? It depends on the business

For a zoo, DOG is an instance of ANIMAL. For a dog breeder, DOG is the entity and TERRIER, POODLE, LABRADOR are its instances.

Attribute

  • A specific piece of information that helps describe, quantify, qualify, classify or specify an entity.
  • Has a single value at any one time for each instance. Values have a data type (number, string, date, image, sound…).
  • Volatile attributes change constantly (age). Nonvolatile rarely change (order date). Prefer nonvolatile: store birth date, not age.
  • Mandatory attributes must have a value (name). Optional ones may be null (cell phone). The same attribute can be mandatory in one system and optional in another (email for EMPLOYEE in an email app vs CUSTOMER in an online catalog).
EntityExample attributes
CUSTOMERfamily name, date of birth, shoe size, town of residence, email
CARmodel, weight, catalog price
ORDERorder date, ship date
TRANSACTIONamount, transaction date
EMPLOYMENT CONTRACTstart date, salary

Unique identifier (UID)

A single attribute or a combination of attributes that distinguishes one instance from another. In a classroom, the student's admin number.

Identifying Relationships DD 3-1

Relationships:

  • Represent something of significance to the business and show how entities are related.
  • Exist only between entities, or between an entity and itself.
  • Are bidirectional and named at both ends.
  • Have optionality and cardinality.

Optionality · must or may?

Ask for each side: must every EMPLOYEE have a JOB? and must every JOB be assigned to an EMPLOYEE? Yes → mandatory.

Cardinality · how many?

Ask: how many JOBs can one EMPLOYEE hold? Only answers one or more than one, never a specific number.

Each EMPLOYEE must hold one and only one JOB · Each JOB may be held by one or more EMPLOYEEs

Restaurant scenario

A customer places an order at the counter, for themselves or for others too (a mother orders for her kids, she owns the order and pays). Over time a customer can place as many orders as they want.

Each CUSTOMER must place one or more ORDERs · Each ORDER must be placed by one and only one CUSTOMER

Relationship to itself

Every employee has one manager (the MD manages themselves). Each manager can manage several employees.

Managers are employees too, so it's one entity: Each EMPLOYEE may be managed by one and only one EMPLOYEE. Each EMPLOYEE may manage one or more EMPLOYEEs.

SEAT/PASSENGER: each SEAT may be sold to one or more PASSENGERs (overbooking!); each PASSENGER may purchase one SEAT.

ER diagramming conventions DD 3-2

ER diagrams are a shared convention, like international road signs. People phrase things differently but everyone draws ERDs the same way.

  • Entities → softboxes, name inside, singular, ALL CAPS (EMPLOYEE, JOB, DEPARTMENT).
  • Attributes listed under the name: * mandatory, o optional, # UID.
  • Relationships → lines. Solid / dashed shows optionality. Single toe / crow's foot shows cardinality.

HR system. Commission is optional because only some employees earn it.

⚠️ Common mistake

Optionality is read from the line half nearest your starting entity. Cardinality is read from the symbol at the other entity's end. Don't mix them up.

⚠️ Where optionality sits

In Barker, optionality is the line half near the entity you start from. In Crow's Foot and UML, both symbols sit at the far end. So "each employee must work in one department" puts UML's 1..1 next to DEPARTMENT.

Barker extras from the reading: only binary relationships (between two entities) are allowed; a UID bar means the relationship is part of the identifier at that end; a diamond marks nontransferable (a CHAPTER can't move to another BOOK).

Supertypes & Subtypes DD 4-1

  • Supertype: an entity that can be split into more specific groups. Used when some instances have attributes or relationships that others don't. Common attributes and relationships sit at supertype level.
  • Subtype: a more specific group inside the supertype. It inherits all attributes and relationships of the supertype, usually has its own too, is drawn inside the supertype, never exists alone, and may have subtypes of its own.
  • Real-world examples: food orders (eat in, to go), grocery bags (paper, plastic), payments (check, cash, credit). Think of "choices of something".

Example 1 · PAYMENT

Only CREDIT CARD has a card number. CUSTOMER relates to CHECK and CREDIT CARD only, so those lines go to the subtype boxes.

Example 2 · EXAM

STUDENT takes EXAM (relationship at supertype → all three subtypes inherit it). BONUS QUESTION relates to QUIZ only.

The two subtype rules

Exhaustive

Every supertype instance is also an instance of one of the subtypes. No omissions.

STUDENT → FRESHMAN, JUNIOR, SENIOR is not exhaustive if GRADUATE STUDENTs exist.

Mutually exclusive

Each instance belongs to only one subtype at a time.

TRAFFIC LIGHT → RED, YELLOW, GREEN. Can't be red and green at once.

  • A single subtype is the same as the supertype, so there are always 2+ subtypes.
  • At the conceptual stage, add an OTHER subtype to stay exhaustive (WALL COVERING → PAINT, WALLPAPER, FABRIC, OTHER).
  • Any entity can be subtyped; only do it when the business needs to show similarities and differences.
  • Three checks: Is the subtype a kind of supertype? Have I covered all cases (exhaustive)? Does each instance fit one and only one subtype (mutually exclusive)?
  • Nested subtypes are allowed (ANIMAL → VERTEBRATE → BIRD, REPTILE, MAMMAL, OTHER). Usually keep to two levels for readability.
💡 Terminology from the slides

Enhanced ER (EER) model extends the ER model with supertypes/subtypes. Attribute inheritance: subtype entities inherit the values of all supertype attributes, and an instance of a subtype is also an instance of the supertype.

Relationship transferability DD 5-1

  • Transferable: an instance of A can be moved to another instance of B. STUDENT can move to another STUDY GROUP. An EMPLOYEE can transfer DEPARTMENT.
  • Nontransferable: it can't be moved. A RECEIPT issued to a STUDENT can't be given to another student (if wrong, cancel it and write a new one). A POEM's AUTHOR can't change.
  • Relationships are transferable by default. Draw a diamond ◇ for nontransferable, normally on the crow's foot side.

Nontransferable: the diamond sits on the RECEIPT (crow's foot) side

Whether something is transferable is a business rule. Some health clubs let memberships transfer, others don't.

Relationship types DD 5-2

  • 1:M Most common. EMPLOYEE assigned to DEPARTMENT.
  • M:M Common in first versions. STUDENT learns from TEACHER. All M:M get resolved later and disappear.
  • 1:1 Rare. Appears for roles (PERSON acting as TEACHER / STUDENT; mandatory at one end) and processes (EXAM ↔ ANSWER KEY, RECIPE ↔ DISH).

Redundant relationships

A relationship that can be derived from other relationships. COUNTRY → TOWN → PERSON already tells you a person's country, so a direct COUNTRY–PERSON "living in" line is redundant. Remove it.

⚠️ Read the names before deleting

If PERSON is born in a COUNTRY but lives in a TOWN, the direct line means something different, so it's not redundant. Don't judge from the shape alone.

Resolving M:N relationships DD 5-3

A STUDENT may study one or more SUBJECTs. Each SUBJECT may be studied by one or more STUDENTs. Where does "Grade" go?

Not STUDENT (which subject?) and not SUBJECT (which student?). The M:M relationship is hiding an attribute.

  1. Create the intersection entity (ENROLLMENT) and put Grade in it.
  2. Replace the M:M with two 1:M relationships. The crow's feet point at the intersection entity.
  3. Identify the UID of the intersection entity. Often it comes from the original entities via barred relationships (Student ID + Subject ID).

The bars next to ENROLLMENT show both relationships are part of its UID

TermDefinition
Intersection entityThe product of resolving a many-to-many relationship
Barred relationshipA relationship that participates in an entity's unique identifier

More examples: TV SHOW ↔ PERSON resolved by VIEWING RECORD; CLEANING COMPANY ↔ CLEANING SERVICE resolved by CLEANING SCHEDULE.

CRUD requirements DD 5-4

  • The ERD is the conversation tool between consultant and client, and the blueprint for the DBA.
  • CRUD analysis validates the ERD: Create, Retrieve, Update, Delete are the four basic database operations.
  • A business rule with no entity to CRUD against → model is incomplete.
  • An entity not touched by any CRUD function → you may not need it (out of scope).

Artificial, Composite & Secondary UIDs DD 6-1

  • Simple UID: one attribute (CONCERT TICKET # Ticket number). Composite UID: a combination (# Date of performance + # Seat number).
  • Artificial UID: doesn't occur naturally, created for identification (Admin Number, NRIC, Customer ID, Shoe ID). First + last name usually isn't unique, so create one. A UID can be both artificial and composite.
  • UID from a barred relationship: attribute + relationship. ACCOUNT # Number + BANK, because two banks can issue the same account number (transfers need the bank routing number too).
  • An intersection entity can use an artificial UID instead of bars: CATALOG ITEM # Number resolves MANUFACTURER ↔ PRODUCT, and its relationships are not barred.
  • Candidate UIDs: two or more possible UIDs (customer code, email). The one chosen is the primary UID; the rest are secondary UIDs.

One primary, one secondary UID

Two secondary UIDs, #2 is composite

UIDs become primary keys in the database. In the real world, telling things apart is not always this easy.

Normalization & First Normal Form DD 6-2

Storing a friend's phone number in three places means three updates when it changes, and you won't know which copy is right if one is missed. Normalization removes this redundancy. Goal: "store information in one place and in the best possible place."

📌 1NF rule

No multi-valued attributes. Check that each attribute has a single value for each instance. If one is multi-valued, create a new entity and relate it with a 1:M relationship.

✗ Not 1NF. Many classrooms per building.

✓ 1NF. CLASSROOM is its own entity.

Second Normal Form DD 6-3

📌 2NF rule

1. Entity is already in 1NF.
2. Every non-UID attribute depends on (is a property of) the entire UID. Ask "is X a property of part A, part B, or both?" 2NF needs "both" every time.

2NF problems only happen with a composite UID. If the UID is one attribute, there's no "part" of it to depend on.

PRODUCT SUPPLIER

If one supplier supplies 5 products, the name is stored 5 times

Purchase price depends on both → stays. Supplier name depends only on supplier → moves. Note the bar.

More 2NF violations

  • ACCOUNT (# Number + barred BANK): balance and date opened depend on both ✓. Bank location depends on BANK only ✗ → move it to BANK. Otherwise every account at that bank needs updating if the bank moves.
  • ORDER LINE (barred to ORDER and PRODUCT): item price depends on PRODUCT only ✗ → move to PRODUCT.
  • PRODUCT SUPPLIER + Supplier Address: property of SUPPLIER only ✗.

Table version (prime / non-prime)

  • Prime attribute: part of a candidate key. Non-prime: not part of any candidate key.
  • 2NF: table is in 1NF and no non-prime attribute depends on a proper subset of any candidate key.

Candidate key {teacher_id, subject_id}. teacher_gender depends on teacher_id alone → violates 2NF. Split into TEACHER(teacher_id, teacher_gender) and TEACHER_SUBJECT(teacher_id, subject_id, stu_feedback).

Third Normal Form DD 6-4

📌 3NF rule

1. Entity is already in 2NF.
2. No non-UID attribute depends on another non-UID attribute. In other words: no transitive dependencies, and non-UID attributes can't have attributes of their own.

CD collection

Store address depends on store name (non-UID) → transitive

✓ 3NF. STORE is its own entity.

More 3NF examples

  • CITY (Name, Size, Population, Mayor, State, State flower): state flower belongs to STATE ✗ → new STATE entity (# Id, Name, Flower). CITY in STATE.
  • EMPLOYEE (…, o Partner name, o Partner birth date): birth date is an attribute of the partner ✗ → new PARTNER entity (# Name, * Birth date). The 1:1 is optional at EMPLOYEE (not everyone has a partner) and mandatory at PARTNER (only tracked if partner of one employee).

3NF solution for the partner example

Table version (superkeys)

  • Superkey: any set of columns whose values are unique across rows. {emp_id}, {emp_id, emp_name}, …
  • 3NF: table is in 2NF and transitive functional dependency of non-prime attributes on any superkey is removed.

employee_details(emp_id, emp_name, emp_zip, emp_state, emp_city, emp_district): state, city and district depend on emp_zip, which depends on emp_id → transitive. Split into EMPLOYEE(emp_id, emp_name, emp_zip) and EMPLOYEE_ZIP(emp_zip, emp_state, emp_city, emp_district).

💡 Quick test for any attribute

1NF: can it hold more than one value? → new entity.
2NF: does it depend on only part of a composite UID? → move it to that part's entity.
3NF: does it describe another non-UID attribute? → make that attribute an entity.

MySQL install & modeling

Install

  • Download the MySQL Installer from dev.mysql.com/downloads/installer (Mac: find the macOS installer on MySQL Community).
  • Choose FULL installation. If you picked "Server Only", install MySQL Workbench separately.
  • On the download page pick the larger community installer (full offline package) and click "No thanks, just start my download"; no Oracle account is needed.
  • Leave the defaults: host localhost, port 3306, user root.
  • Remember the root password you set. After install, Workbench auto-creates the localhost connection; test it with that password.

Model → tables (your assignment submits the DDL)

  1. File → New Model. Use or rename the default schema.
  2. Add Table for each entity. Add a column per attribute (e.g. STUDENT: STUDENT_ID, NAME).
  3. Pick a datatype for each column. Tick PK (Primary Key = UID) and NN (Not Null = mandatory).
  4. The model does not create tables by itself. Go to Database → Forward Engineer (only visible with the model open).
  5. Next → enter password → Next. The wizard shows the generated SQL script (DDL); DBAs usually only need this script.
  6. Enter password again, wait, then check the Schemas tab (hit refresh if tables don't show).

What Forward Engineer generates (the DDL)

CREATE SCHEMA IF NOT EXISTS `mydb` DEFAULT CHARACTER SET utf8;
USE `mydb`;

CREATE TABLE IF NOT EXISTS `mydb`.`STUDENT` (
  `STUDENT_ID` INT NOT NULL,          -- # UID  → PK, NN
  `NAME` VARCHAR(45) NOT NULL,        -- * mandatory → NN
  PRIMARY KEY (`STUDENT_ID`))
ENGINE = InnoDB;

Check it worked in a query tab: USE mydb; SELECT * FROM student;
